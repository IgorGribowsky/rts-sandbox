# T-016 · Переосмыслить систему способностей: данные в ScriptableObject, логика вне

## Что нужно
В файле `UnitSkills.cs` стоит пометка автора: «There are a lot of
architecture problems in this file. So it should be reworked in future».
Подтверждено в чате 2026-09-05: «сейчас очень плохо сделано», нужна
переработка, а не точечные правки.

Правила, которым должна отвечать новая система (ответ в чате 2026-09-05):

1. **Логика не живёт в ScriptableObject.** Сейчас наоборот: `SkillAction`
   это `ScriptableObject` с методом `Act()`, то есть исполняемый код и
   ассет — одно и то же.
2. **Каждая способность и каждый эффект заводятся ассетом.** Пользователь
   создаёт ассет и правит в инспекторе только характеристики. Заводить
   новую способность правкой кода нельзя.
3. **ScriptableObject не меняется из игры.** Сейчас нарушено:
   `UnitSkills.SetupNavigationProperties` в `Start` каждого юнита пишет
   ссылки `Skill` и `SkillAction` прямо в общий ассет. Каждый новый юнит
   переписывает их заново, а в редакторе запись остаётся в ассете после
   выхода из Play mode.

Первые два требования вместе означают одно: ScriptableObject становится
**чистыми данными** (числа, ссылки на префабы, набор импактов), а исполнение
переезжает в обычные классы, которые эти данные читают. Ассет описывает
«что за способность», рантайм-объект — «что происходит прямо сейчас».
Это же снимает и третье требование: писать в данные будет некому.

Что ещё видно из кода и стоит починить заодно:

- кулдаун и текущее состояние лежат в `UnitSkill` внутри публичного
  сериализуемого списка `Skills` — состояние боя вперемешку с настройкой;
- список запрещённых клавиш `banned` продублирован здесь и в
  `WindowsInputController.usedKeys`, и списки не совпадают;
- `UnitsController` держит выбор кастера (`TryGetSkillCaster`,
  `prepearedSkill`) с авторской пометкой, что это просится в отдельный
  `SkillController`.

Задача крупная, почти наверняка разобьётся на подзадачи. Связана с T-001:
эффекты с длительностью проектируются под ту же схему «ассет это данные,
состояние на юните», и делать их дважды не хочется.

## Как проверить
Завести новую способность одним только созданием ассетов, без правки кода.
Кастер кастует все три существующие способности, кулдауны и мана считаются
верно. После выхода из Play mode `git status` показывает, что ни один
ассет в `SkillsSection/` не изменился.

## Решения

- 2026-09-05 найдено при `/adopt`. Пометка про запись в ScriptableObject
  из `Start` — находка при чтении, автором отмечена не была.
- 2026-09-05 (ответ в чате) три требования: логика вне ScriptableObject,
  каждый эффект и способность создаются ассетом, ассеты не меняются из
  игры. Читаю это как «ассет = данные, исполнение = отдельные классы».
  Если имелось в виду другое разделение — поправь до того, как возьму.
- Порядок с T-001 решать при взятии: либо сначала переработка, потом яд
  уже по-новому, либо яд как есть и переделка вместе с ним.
- 2026-09-06 (ответ в чате) сначала переработка, T-001 после неё и уже
  по-новому. Заглушка `PoisonDamageImpact` с `NotImplementedException`
  живёт до T-001.
- 2026-09-06 (ответ в чате) задача разбита на три подзадачи: T-016.1 (ассет —
  чистые данные, исполнение в классах), T-016.2 (состояние каста на юните,
  запись в ассет убрана), T-016.3 (SkillController и единый список занятых
  клавиш). Сам T-016 в работу не берётся: он родитель и закрывается, когда
  закрыты все три.
- Форму разделения беру ту же, что принята для поведений в T-021: тип в
  enum, один явный factory-switch, класс-исполнитель рядом. Рефлексии нет —
  её срезает code stripping в билде.

## Итог

Три правила из M-015 выполнены все. Ассет способности — чистые данные;
исполнение живёт в обычных классах за фабриками; из игры в ассет больше
никто не пишет. Побочно: `UnitsController` перестал знать о способностях,
занятые клавиши перечислены в одном месте, а фильтр целей выехал из класса
снаряда в отдельный `SkillTargetFilter`.

Осталось несделанным сознательно: яд по-прежнему заглушка (T-001, так
решено в чате 2026-09-06).
