# Сохранения и настройки

Прогресс и настройки — два разных файла. Сброс настроек не стирает рекорд,
перенос сейва не тащит чужую чувствительность мыши.

## Решения проекта

- Файлы — в `Application.persistentDataPath`, пути только через
  `Path.Combine`. Рядом с билдом не пишем.
- Формат — текстовый JSON. `BinaryFormatter` запрещён. `PlayerPrefs` — только
  для двух-трёх флагов, не для настроек целиком.
- Запись атомарная: временный файл → проверка → замена основного, прошлый
  остаётся резервным. Чтение: основной → резервный → дефолты, и в последнем
  случае игроку говорится, что сейв не прочитался. Молча с нуля — нельзя.
- Сохранение — событие (конец забега, рекорд, выход из настроек, пауза),
  а не каждый кадр.
- В файле поле версии с первого дня. Старая версия — перенос по шагам и
  пересохранение; новее текущей — резервный или дефолты, и сказать.
  Поле без переноса не переименовывается.
- Сериализация и перенос версий — чистый C# в сборке правил: это логика
  «дано файл → получилось состояние», на неё пишутся тесты (`rules-tests`):
  круг сохранил-загрузил, старая версия, битый файл.

## Грабли

- Статический менеджер хранит данные прошлого запуска Play. Domain Reload
  не отключаем; у менеджера явный сброс при старте игры. Ленивая
  инициализация «если пусто» не спасает — не пусто, там старое.
- Настройка записана, но не применилась до перезапуска. Применение —
  отдельное действие, вызывается и при изменении, и при загрузке на старте.
- Громкость — через группы микшера, не по источникам.
- Значения при чтении приводятся к допустимому диапазону: файл могли
  поправить руками.
- Привязки управления — отдельно от прочих настроек.

## Чем проверить фактами

- Файл по фактическому пути существует, содержимое совпадает с игрой.
- Тесты формата зелёные, включая битый файл и старую версию.
- Настройка применилась сразу — прочитай значение в микшере или компоненте.
- «Рекорд сохранился между запусками» — сценарий приёмки: выйти из игры
  полностью и зайти снова.
