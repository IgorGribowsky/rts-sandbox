# Тесты правил

Тесты — твои глаза на логику. Плейтест пользователя ловит ошибки ощущений,
а тихие ошибки правил — «урон считается не так», «ресурс ушёл в минус» —
ловятся тестом за миллисекунды, до того как он сядет играть.

## 1. Что тестировать

Критерий один: **код по правилам вычисляет результат из входных данных.**
Можно написать «дано X → должно получиться Y» — тест нужен.

Тестируешь: формулы, счётчики и лимиты ресурсов, переходы состояний,
порядок ходов и фаз, условия победы и поражения, генерацию с фиксированным
seed, сериализацию и перенос версий сохранений.

Не тестируешь: вид и ощущение (UI, VFX, звук, камера), сборку в Unity
(сцены, префабы, ссылки в инспекторе), физику, геттеры и перекладывание
данных. Это проверяют снимок, чтение значений и плейтест.

В задаче такой логики нет — тестов нет. Не пиши тесты ради отчёта.

## 2. Откуда берутся ожидаемые числа

**Из доки механики, не из кода.** Тест, в который ожидание скопировано из
только что написанной реализации, проверяет сам себя и проходит всегда.
Числа в доке нет — это вопрос замысла, а не повод взять число из кода.

На правило 2-5 тестов: обычный случай с числами из доки, граница (ноль,
максимум, пустой список), и по одному на каждый пойманный баг. Имена — по
правилу, английские: `Damage_IsReducedByShield_NotBelowZero`.

Тест упал после правки — сначала выясни, кто прав. Правило поменялось
только если поменялась дока, и это решение пользователя. Подгонять тест
под код, чтобы позеленел, нельзя.

## 3. Устройство — настраивается один раз

- Пакет `com.unity.test-framework`. Нет в `Packages/manifest.json` — добавь
  штатно (инструмент пакетов MCP или менеджер пакетов), дождись, пока Unity
  его разрешит, скажи об этом одной строкой.
- **Сборка правил:** `Assets/_Project/Scripts/Rules/` со своим asmdef
  (`<Game>.Rules`). Внутри — обычные C#-классы без `MonoBehaviour` и без
  доступа к сцене. Основной код видит её автоматически.
- **Сборка тестов:** `Assets/_Project/Tests/EditMode/` с asmdef только для
  редактора, со ссылкой на сборку правил и на тестовые сборки Unity.
  Тесты в основную сборку проекта не кладутся: оттуда их не видно.
- Правила получают значения, а не ассеты: компонент читает конфиг и передаёт
  числа внутрь. Тогда тесту не нужны ScriptableObject-ы и сцена.
- На живом проекте правила ещё не вынесены — вынести их целиком это крупный
  рефакторинг, на него нужен апрув (CLAUDE.md). В рамках задачи выносишь
  только ту логику, которую трогаешь; остальное — задача в бэклог.
- PlayMode-тесты не пишешь: медленные и нестабильные. Только EditMode.

## 4. Прогон

- Запуск — инструментом MCP для тестов, имя из живой схемы сессии. Только
  EditMode, по возможности только затронутые тесты.
- Из результата читаешь только упавшие: имя теста и сообщение. Полный отчёт
  и стектрейсы зелёных не нужны.
- Инструмента нет — скажи об этом. Прогон из командной строки требует
  закрытого редактора; не делай его сам, пока пользователь в Unity.
- Красный тест = задача не сделана, как и красная консоль.

## Чем проверить фактами

- Прогон показал: сколько тестов, сколько упало. В чат одной строкой —
  «тесты правил: 12, все зелёные».
- Каждое ожидаемое число в тестах можно найти в доке механики.
- Тест на исправленный баг до фикса падал — ты это видел, а не предположил.
