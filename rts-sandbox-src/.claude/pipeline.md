--------------------------------------------------------------------------------
  Режимы install.js
--------------------------------------------------------------------------------

  node install.js <путь> --dry-run
      Ничего не менять, только напечатать, что будет сделано. Работает
      с любым режимом.

  node install.js <путь>
      Обычный запуск. Режим определяется САМ по содержимому папки, и
      установщик печатает, какой выбрал и почему. Три исхода:

      НОВЫЙ ПРОЕКТ (папки нет, пустая, или лежит распакованный шаблон)
        Распакует unity-template.zip, если папка пуста. Разложит файлы,
        поставит git-файлы, git init, ветка main, коммит «template», потом
        коммит «pipeline <версия>».
        Шаблон ищется рядом с install.js под именем unity-template.zip;
        другое имя или место — флаг --template <путь к zip>.

      ВНЕДРЕНИЕ (в папке проект Unity со своим кодом)
        Только файлы пайплайна, без пустых доков — их соберёт /adopt.
        Свой CLAUDE.md проекта сохраняется, блок правил дописывается в конец.
        Существующий .gitignore не затирается: рядом ляжет .gitignore.pipeline-new.

      ОБНОВЛЕНИЕ (в проекте уже есть .claude)
        См. ниже.

  node install.js <путь> --new | --adopt | --update
      Заставить конкретный режим, если не согласен с выбором. Установщик
      скажет, что выбрал бы сам, и подчинится.

  node install.js <путь> --update
      Обновить пайплайн в проекте, который уже в работе.
      Перезапишет: skills/ commands/ scripts/ templates/ pipeline.md,
                   .gitignore .gitattributes .editorconfig,
                   блок правил в CLAUDE.md
      НЕ ТРОНЕТ:   concept/ docs/ tasks/ handoff/ references/
                   milestones/ state.md и шапку CLAUDE.md с описанием игры

  node install.js <путь> --adopt
      Внедрение в существующий проект принудительно. В норме флаг не нужен:
      скрипт сам видит свой код в Assets и выбирает этот режим.

--------------------------------------------------------------------------------
  Зачем нужен --update и что такое версии пайплайна
--------------------------------------------------------------------------------

Проект живёт месяцами. За это время ты найдёшь косяки в скиллах, добавишь
правила, улучшишь доску. Без --update все улучшения достанутся только новым
проектам, а тот, что в работе, останется на версии, с которой начинался.

  .claude/PIPELINE_VERSION      какая версия пайплайна стоит в ЭТОМ проекте

  Как работать:
  1. Улучшил пайплайн у себя, поднял версию, перепаковал архив.
  2. Зашёл в рабочий проект: node install.js <путь> --update
  3. Скрипт печатает, что поменялось между твоей версией и новой.
  4. Смотришь git diff. Не понравилось — git checkout, откатился.
     Именно поэтому обновление делается на чистом дереве, без незакоммиченного.

  Миграции. Если поменялся ФОРМАТ содержимого — например у задач появилось
  новое поле — скриптом это не переносится, там нужны решения. Тогда скрипт
  ставит новую механику и печатает «нужна миграция содержимого», а переносит
  уже команда в Claude. Такие случаи будут редко, но врать про них не буду.

--------------------------------------------------------------------------------
  Как выложить проект на GitHub
--------------------------------------------------------------------------------

install.js делает только локальный репозиторий. Твой обычный порядок
работает без изменений:

  1. Создал на GitHub ПУСТОЙ репозиторий — без README, без .gitignore,
     без лицензии. Иначе первый пуш упрётся в расхождение историй.
  2. git remote add origin <ссылка>
  3. git push -u origin main

Дальше как всегда. Пайплайн (.claude/ и CLAUDE.md) едет в репозиторий
вместе с проектом — это правильно, история решений хранится с кодом.

Работать руками можно, пайплайн этому не мешает. Но есть одно правило,

================================================================================
  ПРИЛОЖЕНИЕ А. КАК СОБРАТЬ МИНИМАЛЬНЫЙ ШАБЛОН UNITY
================================================================================

Делается один раз. Дальше только правишь и перепаковываешь.

Идея минимальности: в архив едут ТОЛЬКО Assets, Packages, ProjectSettings
и корневые dot-файлы. Пакеты в архиве лежат не содержимым, а двумя
конфигами — manifest.json (что нужно) и packages-lock.json (каких именно
версий). Реальные пакеты живут в глобальном кеше Unity и при первом
открытии проекта восстанавливаются оттуда или докачиваются. Встроенные
модули вообще идут с редактором. Так что «только конфиги» — да, работает,
но первое открытие требует интернета.


--------------------------------------------------------------------------------
  А.1. Три развилки, которые решаются один раз
--------------------------------------------------------------------------------

  1. ВЕРСИЯ UNITY. Только LTS, не Tech Stream. В LTS меньше багов редактора
     и стабильнее пакеты, а Tech Stream существует для тех, кому нужны
     свежие фичи ценой сюрпризов. Версия пинится файлом ProjectVersion.txt
     и меняется осознанно, а не при обновлении Hub.

  2. РЕНДЕР-ПАЙПЛАЙН. Нужна пост-обработка (блум, свечение, цветокоррекция) —
     URP: всё это есть из коробки через Volume. Built-in дешевле и проще,
     но за блум придётся тащить Post Processing Stack v2 отдельно. Обратная дорога болезненная: смена пайплайна ломает
     все материалы, поэтому решай сейчас, а не на пятой задаче.

  3. INPUT SYSTEM (новый) вместо старого Input Manager. Он умеет несколько
     схем управления, перебиндинг клавиш и любые устройства, включая те,
     про которые ты сейчас не думаешь. Старый Input Manager не умеет ничего
     из этого, а переезжать потом дороже, чем начать сразу.


--------------------------------------------------------------------------------
  А.2. Создать проект
--------------------------------------------------------------------------------

  Unity Hub -> New project -> шаблон (URP или 3D/2D Built-in) -> создать
  в отдельной папке ВНЕ рабочих проектов, например C:\Templates\unity-base

  Дальше вычищаешь то, что натащил шаблон Unity Hub: демо-сцены, примеры
  ассетов, готовые материалы и префабы шаблона. Оставляешь только то, что
  нужно пайплайну — настройки URP-ассета, если URP, и ничего больше.


--------------------------------------------------------------------------------
  А.3. Настройки проекта — самое важное
--------------------------------------------------------------------------------

Первый пункт критичен для работы с ИИ. Без него ревью диффа и откаты
работают вполсилы или не работают вообще.

  [!] Project Settings -> Editor -> Asset Serialization -> Mode: FORCE TEXT
      Без этого сцены и префабы сохраняются в бинаре, не диффятся, и
      «посмотреть что изменилось» и «осмысленно откатить» становится
      невозможно. Самая важная настройка во всём шаблоне.

  Project Settings -> Editor -> Line Endings For New Scripts: UNIX
      Обычно стоит OS Native. Чтобы новые файлы не приносили CRLF в
      репозиторий.

  ВИДИМЫЕ .META-ФАЙЛЫ
      Раньше это была отдельная настройка Version Control -> Visible Meta
      Files. В новых версиях Unity видимые .meta — поведение по умолчанию,
      а сама секция показывается только при установленном пакете Version
      Control от Unity, который мы всё равно выкидываем. Секции нет —
      значит всё в порядке. Проверить фактом: рядом с папками и файлами
      в Assets лежат файлы *.meta. В них GUID; потеряешь — отвалятся все
      ссылки в сценах и префабах, поэтому в .gitignore они не попадают
      никогда.

  ЭТО НАСТРОЙКА РЕДАКТОРА, А НЕ ПРОЕКТА, И В ШАБЛОН ОНА НЕ ПОПАДАЕТ:
  Edit -> Preferences -> General -> Script Changes While Playing:
                                   RECOMPILE AFTER FINISHED PLAYING
      Ты играешь, ИИ в этот момент правит скрипт, Unity начинает
      перекомпиляцию посреди Play mode и состояние игры плывёт. Ловится
      как «мистический баг», которого нет.
      Живёт в настройках редактора, действует сразу на все проекты и в
      ProjectSettings не сохраняется. Выставляешь один раз на машине;
      на новом компьютере придётся выставить заново.

  Player -> Other Settings -> Color Space: LINEAR
      Нужно для корректного блума и вообще всего пост-эффектного.
      Менять потом на живом проекте — перекрасить всё заново.

  Player -> Product Name: оставь заглушку, /intake впишет название игры
  Player -> Version: 0.0.0
  Player -> Company Name: свою, один раз

  Build Settings: одна пустая сцена Assets/_Project/Scenes/Main.unity,
  индекс 0, больше ничего.

  НЕ ТРОГАЙ: Enter Play Mode Settings — там должно остаться значение
  по умолчанию, Reload Domain and Scene. Отключение Domain Reload
  Ускоряет вход в Play mode заметно, но статические поля перестают
  сбрасываться между запусками — а у тебя статический SaveManager из
  наработок. Получишь тихие баги, которые не воспроизводятся после
  перезапуска редактора. Оставь дефолт.

  Численные значения в файлах настроек (m_SerializationMode и прочие)
  по памяти не выписываю — выставь галочки в редакторе глазами и потом
  сверь, что ProjectSettings/EditorSettings.asset реально изменился.


--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

ПРИНЦИП. Шаблон нейтрален: на момент его сборки игры ещё нет, и решать
за неё нельзя. Поэтому выкидываем ТОЛЬКО то, что решено самим пайплайном
и не зависит от замысла. Всё, что «может понадобиться, а может нет»,
ОСТАЁТСЯ: лишний пакет весит мегабайты, а доставлять нужный в проект,
который уже месяц пишется, неприятнее, чем удалить ненужный в начале.

Package Manager -> In Project. Убрать:

  com.unity.feature.development   бандл, тянет за собой test framework,
                                  performance testing и прочее
  com.unity.test-framework        автотестов нет вообще — решение пайплайна
  com.unity.nunit                 остаток от test framework
  com.unity.test-framework.performance   то же
  com.unity.visualscripting       ИИ пишет код, а не блок-схемы
  com.unity.collab-proxy          Version Control от Unity; git у тебя снаружи
  com.unity.multiplayer.center    сетевой сервис Unity, не про игру
  второй IDE-пакет                нужен один — тот, в котором смотришь код

Оставить:
  com.unity.inputsystem           см. А.1
  com.unity.ugui                  UI, в новых версиях включает TextMeshPro
  com.unity.render-pipelines.universal   если выбрал URP
  один IDE-пакет (rider или visualstudio) — нужен только для генерации
  csproj, чтобы у редактора кода было понимание проекта

  И ВСЁ ОСТАЛЬНОЕ ТОЖЕ, в том числе:
  com.unity.timeline              катсцены. Понадобятся — уже стоит
  com.unity.ai.navigation         NavMesh: поиск пути в обход препятствий.
                                  Нужен всему, где персонажи ходят по
                                  геометрии. Не нужен, если движение простое

  Mono Cecil                      зависимости URP и Shader Graph, отдельно
                                  не удаляются и трогать их не надо

  Конкретной игре что-то из оставленного не нужно — это выяснится на
  /intake вместе с остальным тех-дизайном, и выкинет это уже ИИ, зная,
  что за игра.

  Встроенные модули (com.unity.modules.*) не трогай вообще. Выкинуть

  После чистки проверь, что packages-lock.json обновился и лежит рядом

--------------------------------------------------------------------------------
  А.6. Файлы для git — В ШАБЛОН НЕ КЛАДЁМ
--------------------------------------------------------------------------------

  .gitignore, .gitattributes и .editorconfig ставит install.js.

  Почему не в шаблоне: они меняются чаще шаблона и одинаковы для всех
  проектов. Держать их в двух местах — гарантированно получить две разные
  версии и не знать, какая правильная.

  Что тебе полезно про них знать:
    - .gitignore игнорирует Library, Temp, obj, Logs, Build, UserSettings,
      мусор IDE и csproj/sln. Главное: *.meta НЕ игнорируются никогда —
      в них GUID, потеряешь их, отвалятся все ссылки в сценах.
    - .gitattributes нормализует переводы строк и помечает бинарники.
      Без него Windows натащит CRLF, файлы попадут в дифф целиком, и
      ревью изменений перестанет что-либо показывать.
    - Git LFS пока не включаем: на модельки аркады объёма мало. Начнёшь
      возить тяжёлый арт — заведём отдельно.
    - Мержилку сцен не настраиваем — работа в одной ветке, мержей нет.

  Library регенерируется при первом открытии. Она весит гигабайты и

================================================================================
  ЧТО ФИКСИРОВАНО, А ЧТО ГЕНЕРИРУЕТСЯ ПОД ПРОЕКТ
================================================================================

Пайплайн — это МЕТОД, а не шаблон игры. Проекты будут разными, и пример
с аркадой выше — только пример, а не форма, в которую всё складывается.

ФИКСИРОВАНО ВСЕГДА (это и есть пайплайн):
  - цикл: идея -> доки -> план -> задача -> приёмка
  - роли: кто решает, кто делает, кто принимает
  - иерархия источников истины
  - устройство задач, чекпоинтов, откатов
  - очередь того, что ждёт тебя, и заглушки под ассеты
  - знание про грабли Unity (где данные портятся молча)
  - дисциплина по токенам

ГЕНЕРИРУЕТСЯ ПОД КАЖДЫЙ ПРОЕКТ:
  - какие доки существуют и что в них
    (обязательны только видение и границы скоупа — без них не собрать план)
  - какие механики и как они устроены
  - сколько версий и какие у них цели
  - задачи, их порядок и размер
  - архитектура и стек
  - что попадает в смоук-чек
  - библиотека скиллов ДОПОЛНЯЕТСЯ: десять базовых — стартовый набор.
    Появилась работа со своей спецификой, которая повторяется, — команда
    /new-skill оформляет её в скилл этого проекта.

Аркада, пазл и рогалик пройдут по одному ритуалу и получат совершенно
разные доки, разное число версий и разные задачи. Метод жёсткий,
содержание свободное. Наоборот не работает: пайплайн, который придумывает
себе процесс под каждый проект, теряет предсказуемость, ради которой
он и нужен.


================================================================================
  ПРИЛОЖЕНИЕ Б. ФОРМАТЫ ФАЙЛОВ
================================================================================

То, что скрипт читает механически. Проза внутри файлов свободная, а эти
поля — нет: сломаешь формат, доска нарисует ⚠ INVALID с именем файла.
Полная схема задачи с правилами валидации — .claude/templates/task-schema.md

Общие правила front-matter: блок между --- в самом начале файла, одна пара
«ключ: значение» на строку, значения — скаляры или инлайн-списки [A, B].
Вложенности и многострочных значений нет намеренно: то, что ИИ пишет,
скрипт обязан прочитать однозначно.
