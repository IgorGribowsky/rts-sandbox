# Схема файла задачи

Не копируется в задачи. Это справка для board.js, команд и скиллов.
Файл задачи создаётся из `templates/task.md`.

Путь: `.claude/tasks/T-004-shooting.md` — `T-<номер>-<короткий-slug>.md`, slug латиницей.
Закрытые и отменённые уезжают в `.claude/tasks/done/` и больше не читаются никогда.


## Правила парсинга front-matter

Скрипт читает ТОЛЬКО front-matter, прозу не парсит. Поэтому формат жёсткий:

- блок между `---` в самом начале файла, первая строка файла — `---`;
- одна пара `ключ: значение` на строку, ключи латиницей в нижнем регистре;
- значения — скаляры или инлайн-список `[A, B]`. Никакой вложенности,
  никаких многострочных значений, никаких YAML-якорей;
- пустое значение = «нет значения». Для списков пустое и `[]` равнозначны;
- кавычки не нужны; если в title есть `:` — берём в двойные кавычки;
- неизвестный ключ не ломает парсер: игнорируется, но попадает в `--validate`.


## Поля

| ключ | обяз. | значение |
|---|---|---|
| `id` | да | `T-004`, у подзадачи `T-004.1`. Неизменяем, не переиспользуется |
| `title` | да | одна строка, русский |
| `status` | да | `todo · in-progress · review · blocked · done · cancelled` |
| `milestone` | да | `v0.0.1` или `backlog` |
| `parent` | нет | `T-012` у подзадачи, пусто у обычной задачи |
| `origin` | да | `user` — заказал пользователь, `ai` — ИИ завёл сам |
| `needs-design` | да | `true` — нужно решение пользователя, в работу НЕ идёт |
| `blocked-by` | нет | `[Q-4]`, `[H-002]`, `[T-007]` — почему `blocked` |
| `mechanics` | нет | `[M-002]` — доки замысла, которые эта задача реализует |
| `handoff` | нет | `[H-001]` — заглушки, оставленные этой задачей |
| `checkpoint` | нет | короткий хеш последнего `cp(T-004)` |
| `created` | да | `ГГГГ-ММ-ДД` |
| `updated` | да | `ГГГГ-ММ-ДД`, дата последней смены статуса |

`updated` нужен ровно для одного: понять, что задачи висят в `review` давно
и пора напомнить про плейтест.


## Статусы: переходы

```
todo ──> in-progress ──> review ──> done
  ^            |            |
  |            v            v
  └───────── blocked      todo        (правки после плейтеста)
  └───────── cancelled
```

- `in-progress` — АВАРИЙНЫЙ статус. В норме задача выходит из него до конца
  сессии. Нашли `in-progress` — был обрыв, это точка входа для `/resume`.
- `review` ставит ИИ. `done` ставит только `/done`, то есть только после
  плейтеста пользователя. ИИ не ставит `done` сам никогда.
- `blocked` требует непустой `blocked-by`.
- `needs-design: true` запрещает `in-progress` при любом статусе.


## Порядок задач и принадлежность версии

Порядок хранится ОДИН раз — списком ID в файле `milestones/vX.Y.Z.md`.
В задаче поле `milestone` — обратная ссылка, чтобы файл задачи читался
в одиночку (нужно для `/resume` и для правила «не переоткрывать задачи
закрытых версий»).

Отсюда следствия:
- переупорядочивание = правка одного файла milestone, задачи не трогаются;
- бэклог — это `milestone: backlog`, отдельного файла-списка у него нет,
  порядок в бэклоге не значим;
- `--validate` обязан ловить рассинхрон: задача заявляет `v0.0.2`, а
  перечислена в `v0.0.1`; заявляет версию, которая её не перечисляет;
  перечислена в двух версиях сразу.


## Подзадачи

Отдельные файлы, `id` с суффиксом: `T-012`, `T-012.1`, `T-012.2`.
Суффикс, а не сквозная нумерация — родство видно в state.md, в имени файла
и в сообщении коммита без чтения front-matter.

- в работу берётся ТОЛЬКО подзадача. Родитель — контейнер;
- у родителя своя `Как проверить`: приёмка целого после приёмки частей;
- прогресс родителя доска считает по детям и рисует `2/4`. Поле `status`
  родителя при этом реальное: `todo`, пока хоть одна подзадача не `done`;
  `review` — когда все дети `done`; `done` — по `/done` на родителя;
- `cancelled` у ребёнка в знаменатель не входит;
- дробить дальше нельзя: `T-012.1.1` не бывает. Нужна такая глубина —
  значит родитель на самом деле milestone, и это разговор с пользователем.

Разбивать, когда задача не влезает в один заход или её нельзя проверить
одним плейтестом. Жёсткого размера в строках и файлах нет.


## ID и валидацию выдаёт скрипт, а не ИИ

`scripts/lib/tasks.js`:
- следующий ID задачи — максимальный существующий номер + 1, считая
  `tasks/` и `tasks/done/`. Номера не переиспользуются никогда;
- следующий ID подзадачи — максимальный суффикс детей этого родителя + 1;
- `board.js --validate` проверяет весь набор и печатает файл и причину.

ИИ номера не придумывает и формат по памяти не проверяет: после любой
правки файлов задач прогоняет `--validate` и исправляет найденное.
Битый `status` доска рисует как `⚠ INVALID` с именем файла и не падает.


## Зависимостей между задачами нет

В раннем черновике формата было поле `depends: [T-110]`. Здесь его нет
намеренно: порядок задач задаёт список в файле milestone, а `/next` не
вычисляет очередь сама — задачу выбирает пользователь курсором на доске.
Второй механизм упорядочивания стал бы вторым источником той же правды.

Реальная блокировка выражается статусом `blocked` и полем `blocked-by`,
куда можно положить и ID задачи: «не могу, пока не сделан T-007».


## Разделы тела файла

`Что нужно` · `Как проверить` · `План` · `Ход работы` · `Решения` · `Итог`

Порядок и заголовки фиксированы — по ним ориентируются команды. Пустой
раздел не удаляется. Лишние разделы не добавляются: если написать некуда,
значит это либо дока, либо вопрос в очередь.

`Решения` — единственное место для «почему так». Ответ пользователя в чате,
влияющий на замысел, идёт в доку; влияющий только на эту работу — сюда.
Оба случая — сразу, с датой и пометкой «ответ в чате».
