## Роли

Пользователь: геймдизайн и все решения, приоритеты, плейтест и приёмка,
ассеты, правки в Unity Editor руками. Код не пишет.

Ты: код, диагностика багов, дешёвая проверка, документация, ведение задач,
черновики дизайна по запросу (пишутся со `status: proposed`).

## Никогда

- не принимаешь дизайн-решения молча;
- не правишь доки в `accepted`/`implemented` без спроса;
- не ставишь `done` задаче из плана — твой финиш `review`, `done` по `/done`
  после плейтеста пользователя (исключение — задача задним числом, ниже);
- не расширяешь скоуп текущей версии: найденное по ходу уходит в бэклог,
  исключение — блокер текущей задачи;
- не пишешь в `concept/` — это зона пользователя. Туда только переносишь
  разобранное в `concept/processed/`;
- не открываешь содержимое `references/` без прямой ссылки пользователя.
  Перечислять имена файлов можно свободно, картинки дорогие;
- не переоткрываешь задачи из закрытых версий — показываешь и спрашиваешь;
- не меняешь несущие настройки Unity: Force Text в проекте и Recompile
  After Finished Playing в настройках редактора;
- не собираешь билды.

Работы без задачи не бывает. Поменял код или ассеты по ходу разговора, вне
задачи — заведи задачу задним числом и закрой её сам, без `/done`: результат
пользователь уже видел в чате. Порядок закрытия — как в `/done`. Ответы на
вопросы и разговоры без правок задачи не требуют.

Взял первую задачу новой версии — сразу поставь `bundleVersion` в её номер
(через `PlayerSettings`, не текстом в ассете). Версия проекта равна версии, над
которой идёт работа, а не последней закрытой.

## Источники истины, при расхождении

```
что реально в игре ..... код и сцены      (главнее доков по факту)
что задумано ........... docs/            (accepted и implemented)
что хочет пользователь . concept/         (пока не перенесено в docs/)
что сделано ............ tasks/ + tasks/done/
почему так решили ...... файл задачи
```

Доки описывают замысел, код описывает факт. Разошлись — покажи расхождение
и спроси. Молча выбрать удобное нельзя.

## Цикл задачи

1. `/next` или `/task T-004`. Читаешь файл задачи и её доки по ID.
2. Чекпоинт-коммит сам, без спроса: `cp(T-004): <краткое что>`.
   Хеш — в `checkpoint` задачи и в `state.md`. Ставишь `in-progress`.
3. В чат 3-5 строк: как понял, что трогаю, чем закончу. Апрува не ждёшь.
   `План` в файле задачи — твой чек-лист на 3-7 пунктов, не для пользователя.
4. Работаешь. Закончил пункт — отметил `[x]`, отступил — строка под пунктом.
5. Дешёвая проверка своими силами: дождался готовности редактора, прочитал
   консоль, прогнал тесты правил, если они есть. Красная консоль или красный
   тест = задача не сделана.
6. `review` + сценарий проверки в чат: что нажать, что должно быть, что
   могло задеть. `review` — не `done`.
7. Правки пользователь пишет обычным текстом, без команд. Правишь в этой же
   задаче и снова `review`.

## Апрув

Спрашиваешь только на трёх вещах:
1. развилка в дизайне — 2-3 конкретных варианта на выбор;
2. риск задеть принятую механику или крупный рефакторинг;
3. изменение скоупа: добавить/убрать задачи, поправить принятые доки.

Всё остальное делаешь и показываешь результат. Главный гейт — приёмка.

## Вопросы к пользователю

Спрашиваешь сразу, как упёрся, батчем, каждый вопрос с 2-3 вариантами и
своей рекомендацией. «Потом», «позже», «не сейчас» = отложить: вопрос
уезжает в `docs/06-open-questions.md`, ты продолжаешь с тем, что можно без
ответа. Совсем нельзя двинуться — задача в `blocked`, берёшь следующую.
Разгребается через `/ask`. Очередь одна на все типы: решения, ассеты, приёмка.

Ответ, полученный в чате, сразу пишешь в файл — с источником «ответ в чате»
и датой. Чат умирает: не записанный ответ потерян. В `concept/` — никогда.

Задачи копятся в `review`, плейтеста давно не было — напомни.

## Проверка

Эти правила общие для всех скиллов, скиллы их не повторяют.

- проверка фактами обязательна: не «по коду должно работать», а прочитал
  фактическое значение с диска и показал его. Что проверяется только
  глазами — так и скажи и вынеси в сценарий приёмки;
- исполнение кода в редакторе — для ЧТЕНИЯ и проверки. Изменения только
  штатными инструментами: правка ассетов кодом в Edit mode молча портит
  конфиги;
- иерархию сцены целиком не запрашиваешь никогда, читаешь точечно;
- консоль по умолчанию: только ошибки, без стектрейсов, с лимитом.
  Стектрейс — точечно, по разбираемой ошибке;
- тесты пишешь только на логику «дано X → должно получиться Y» (формулы,
  ресурсы, переходы состояний, формат сохранений) — скилл `rules-tests`.
  Вид, ощущение и сборку в Unity тестами не проверяешь;
- видимый результат (UI, расстановка в сцене) проверяешь сам снимком
  Game view — это для тебя, пользователю снимки не показываешь;
- `docs/07-smoke-check.md` — памятка пользователя для ручной проверки: ты её
  пополняешь самым важным, но не прогоняешь и прогнать не напоминаешь;
- имена MCP-инструментов нигде не зашиты: живая схема сессии авторитетнее.

## Токены

Всё, что читается на каждом запуске, — постоянного размера, а не размера
проекта. Доки читаешь по ID, а не папкой. `tasks/done/` не читаешь никогда.
Состояние доски — через `node .claude/scripts/board.js --brief`, не чтением
файлов задач. Журналов нет: журнал задачи внутри её файла, история проекта
генерируется из `tasks/done/`.

Памятка `.claude/pipeline/` разбита по частям. Нужна справка — читаешь
`00-index.md`, потом одну нужную часть, не папку целиком.

## Unity руками

У сцены и префаба в данный момент ОДИН владелец. Ты читаешь файл с диска,
несохранённые правки редактора для тебя не существуют, а Unity потом
затрёт твоё своим состоянием из памяти. Поэтому: всегда говори, какие
файлы будешь менять (это те 3-5 строк перед работой), и не работай со
сценой, которую пользователь правит сейчас.

## Где что лежит

```
.claude/state.md          3 строки: задача, следующий шаг, хеш чекпоинта
.claude/pipeline/         памятка по частям, вход — 00-index.md
.claude/project-map.md    навигация по коду, пересобирается /map
.claude/concept/          зона пользователя, идеи в свободной форме
.claude/docs/             замысел. Обязательны видение и границы скоупа
.claude/milestones/       цель версии + упорядоченный список ID задач
.claude/tasks/            открытые задачи, done/ — архив
.claude/handoff/          что ждёт ассетов или решений пользователя
.claude/references/       чужие материалы, без прямой ссылки не открываешь
.claude/{skills,commands,scripts,templates}/
```

## Статусы

Задачи: `todo · in-progress · review · blocked · done · cancelled`.
`in-progress` — аварийный: нашёл его в новой сессии, значит был обрыв,
это точка входа для `/resume`. Флаги: `needs-design`, `origin: ai|user`.

Доки: `proposed · accepted · implemented · cut`. `proposed` — твой черновик,
в работу брать нельзя.

Handoff: `waiting · ready · integrated`, поле `blocking: yes|no`.
При `no` задача проходит обычную приёмку и закрывается с заглушкой.

ID задач не придумываешь и формат по памяти не проверяешь: номер выдаёт
скрипт, а после любой правки файлов задач прогоняешь
`node .claude/scripts/board.js --validate` и исправляешь найденное.

## Команды

`/next` `/task` `/done` `/resume` `/status` · `/intake` `/plan` `/ask` ·
`/handoff` `/rollback` `/map` `/repo-init` `/new-skill` · `/adopt`

«Закрой версию» — не команда, а фраза пользователя: порядок в
`.claude/commands/done.md`, раздел «Закрытие версии».

Доска — не команда, а скрипт во втором терминале: `node .claude/scripts/board.js`

## Язык

Доки, файлы задач, интерфейс доски, общение — русский.
Код, комментарии, идентификаторы, имена файлов кода — английский.
